# 픽스처(가상 데이터)로 테스트하는 방법

## 왜 픽스처가 필요한가

새 기관의 API 키를 아직 못 받았거나, 받았어도 아직 실제로 호출하면 안
되는 상황(승인 대기 등)에서도 "코드가 제대로 동작하는지"는 미리
확인하고 싶을 때가 있다. 이럴 때 실제 API 응답과 비슷한 형태의 **가짜
데이터 파일(픽스처)** 을 만들어두고, 그 파일로만 변환·중복제거·저장
로직을 테스트한다. 실제 사이트에는 전혀 접속하지 않는다.

## 지금 있는 픽스처

| 파일 | 대상 기관 | 비고 |
|---|---|---|
| `collector/fixtures/kocca_sample_response.json` | 한국콘텐츠진흥원 | 필드명이 **추정값**(ASSUMED_FIELDS) 기준 |
| `collector/fixtures/kstartup_sample_response.json` | 창업진흥원(K-Startup) | 필드명이 **추정값** 기준 |

두 파일 모두 맨 위에 `"_is_real_data": false`와 `"_fixture_notice"`가
있다 — 실제 데이터가 아니라는 표시다. 이 표시가 있는 파일은 코드에서도
"진짜 데이터가 아님"을 다시 한번 확인하고 사용한다
(`test_standard_source_pipeline.py`의 첫 번째 검사 항목).

## 실행 방법

```bash
python app/db/test_standard_source_pipeline.py
```

이 스크립트는:
1. 픽스처 파일 2개를 읽는다 (네트워크 없음)
2. 각 어댑터의 `to_standard_program()`으로 변환한다
3. **운영 중인 DB가 아니라 임시 DB**에 적재해본다 (그래서 실제 화면에
   가짜 공고가 섞여 보이는 일이 없다)
4. 중복 제거, 날짜 미확정 처리, DB 반영 결과를 검증한다
5. 마지막에 운영 DB(`app/data/govfunding.sqlite3`)가 이 테스트로 인해
   전혀 바뀌지 않았는지도 함께 확인한다

## 새 기관의 픽스처를 직접 만들려면

1. `collector/adapters/새기관_adapter.py`의 `ASSUMED_FIELDS`를 연다
2. 거기 적힌 키 이름을 그대로 써서 JSON 파일을 만든다 (2~3건이면 충분)
3. 맨 위에 반드시 아래 두 줄을 넣는다.
   ```json
   "_is_real_data": false,
   "_fixture_notice": "이 파일은 실제 API 응답이 아닙니다. ...",
   ```
4. 의도적으로 "이상한 케이스"도 하나 넣어보면 좋다 — 예를 들어
   접수기간이 비어있는 경우, 같은 ID가 두 번 나오는 경우 등. 이런
   케이스가 실제로도 자주 발생하기 때문이다.
5. `test_standard_source_pipeline.py`를 참고해서 같은 방식으로
   테스트 스크립트를 만들거나 확장한다.

## 실제 응답을 받은 뒤에는

실제 키로 딱 1번(5건 이하로 제한해서) 테스트 호출을 해보고 실제 응답
필드명을 확인하면, 그때는 이 픽스처 파일들을 실제 필드명 기준으로
다시 만들거나, "이 픽스처는 v1 추정 스키마였고 실제로는 이렇게 달랐다"
는 메모를 남겨두는 것을 추천한다 — 나중에 왜 필드명이 바뀌었는지
헷갈리지 않게 하기 위함이다.
