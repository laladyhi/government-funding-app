# Phase 1 데이터 모델 설계 — 산업·기관·출처를 하드코딩하지 않는 구조

## 0. 왜 화면보다 데이터 모델을 먼저 확정하는가

화면은 나중에 얼마든지 다시 그릴 수 있지만, 데이터 구조를 잘못 잡으면
나중에 "산업분야 하나 추가하려고 코드를 고쳐야 하는" 상황이 생긴다.
이 문서의 목표는 **산업, 기관, 출처 세 가지를 "코드에 박아 넣지 않고
데이터로 관리"**하는 구조를 확정하는 것이다. 이 구조가 맞으면 화면은
이 구조 위에 얇게 얹히기만 하면 된다.

용어 하나만 먼저: 아래에서 "엔티티"란 DB에서 하나의 표(테이블)로 관리되는
정보 묶음을 말한다. (예: "기관"이라는 엔티티는 "기관 표"에 여러 줄로 저장됨)

---

## 1. 전체 그림

```
[ClassificationAxis 분류축]              [OrganizationType 기관유형]
   (산업분류 / 기술분야분류 / ...)              (정부/중앙부처/산하기관/...)
        │                                          │
        ▼                                          ▼
[ClassificationScheme 분류체계·버전]        [Organization 기관]
        │                                     │        │
        ▼                                     │        │
[ClassificationNode 분류노드] ◄───┐           │   [RelationshipType 관계유형]
  (제조/AI·SW/바이오/... 트리)     │           │     (소속/감독/산하/주관/...)
        ▲                         │           │        │
        │ 다대다                  │           ▼        ▼
[ProgramClassification]           │   [OrganizationRelationship 기관관계]
        │                         │     (출발기관→대상기관, 유형, 확인상태,
        ▼                         │      출처, 확인일, 유효기간, 변경이력)
   [Program 지원사업] ─────────────┘
        │        \
        │         \  다대다 (역할 포함)
        │          ▼
        │   [ProgramOrganizationRole]
        │     (지원사업↔기관, 역할: 주관/공동주관/운영위탁/예산지원)
        ▼
[SourceDocument 원문문서] ──► [FactSource 사실단위 출처]
  (URL/첨부파일/수집일/버전)      (필드명, 값, 문서ID, 페이지/섹션,
                                   확인상태, 사람검수여부)
```

이 그림에서 가장 중요한 두 가지 변화:
1. "기관"이 단순히 `상위기관_id` 하나로 연결되지 않고, **관계 자체가
   독립된 정보(OrganizationRelationship)**로 분리되어 있다.
2. "지원사업 출처"가 사업 전체에 하나 붙는 게 아니라, **항목(필드) 하나
   하나에 개별적으로 붙는다(FactSource)**.

## 2. 산업/기술 분류 구조 (하드코딩 금지 원칙의 핵심)

### 엔티티 정의

**ClassificationAxis (분류축)** — "이게 무엇에 대한 분류인가"의 최상위 구분
- 축 ID
- 축 이름 (예: "산업분류", "기술분야분류")
- 설명

이걸 별도로 두는 이유: 나중에 "정책목적분류"(R&D/수출지원/교육지원 등) 같은
완전히 새로운 분류 축이 필요해져도, 코드를 고치지 않고 축을 하나 추가하는
것만으로 확장된다.

**ClassificationScheme (분류 체계/버전)** — 같은 축 안에서도 분류 기준이
개정될 수 있다 (예: 한국표준산업분류 10차 → 11차 개정)
- 체계 ID
- 소속 축 ID
- 체계명, 버전
- 시행일
- 상태 (현재 사용중 / 이전 버전)

**ClassificationNode (분류 항목/노드)** — 실제 "제조", "AI/SW", "바이오"
같은 개별 항목. 트리(계층) 구조로 자기 자신을 상위 노드로 가리킨다.
- **노드 ID** (내부 고유 식별자 — 한번 만들어지면 절대 바뀌지 않음.
  다른 모든 데이터는 이 ID로만 연결된다)
- 소속 체계 ID
- 상위 노드 ID (자기참조, 최상위는 없음)
- 표준 코드 (있으면 기재, 예: KSIC 코드 — 없어도 무방)
- **표시명** (화면에 실제로 보이는 이름 — 언제든 수정 가능)
- 표시명 변경 이력 (과거 이름들을 기록 — 옛 이름으로 검색해도 찾히게)
- 상태 (사용중 / 폐기됨 / 다른 노드로 통합됨)
- 통합대상 노드 ID (폐기 시, 어느 노드로 흡수됐는지)

**ProgramClassification (지원사업 ↔ 분류노드, 다대다 연결)**
- 지원사업 ID
- 분류노드 ID
- 연결근거 (원문에 명시됨 / AI가 분류함 / 사람이 검수함)
- 확신도 (AI 분류인 경우)

### 이 구조로 무엇이 가능해지는가 (핵심 — 하드코딩 금지 원칙의 실현)

- **새 산업 추가**(예: "반도체"): ClassificationNode에 행 한 줄 추가.
  코드 수정도, 화면 재배포도 필요 없다. 관리자가 데이터 입력 화면(또는
  향후 관리자 도구)에서 이름·상위분류만 정하면 바로 검색·필터에 나타난다.
- **이름 변경/통합**(예: "바이오" → "바이오/헬스케어"로 개명, 또는
  "게임"을 "콘텐츠"에 통합): 노드 ID는 그대로 유지하고 표시명만 바꾸거나
  통합대상을 지정한다. **이미 연결된 수천 건의 공고 데이터는 노드 ID로
  연결되어 있으므로 전혀 깨지지 않는다.** (요청하신 "분류 ID와 표시명
  분리" 원칙이 여기서 실현된다)
- **산업과 기술을 같은 트리 구조로 표현**하되 소속 축(Axis)이 달라 서로
  섞이지 않는다.
- **하나의 지원사업이 여러 산업 + 여러 기술에 동시 연결**된다 (예: "2026
  AI 콘텐츠 제작지원"은 산업축의 "콘텐츠" 노드와 "AI/SW" 노드, 기술축의
  "인공지능" 노드에 동시 연결).

## 3. 기관 및 기관관계 구조

### 엔티티 정의

**OrganizationType (기관유형, 코드 관리)**
- 유형 ID, 유형명 (정부/중앙부처/산하기관/유관기관/지역기관/협회 등)

이것도 고정 목록으로 코드에 박지 않고 데이터로 관리한다 — 나중에
"지자체 출연기관" 같은 새 유형이 필요해도 데이터 추가만으로 확장된다.

**Organization (기관)**
- 기관 ID (내부 고유, 불변)
- 기관명 (표시명, 변경 이력 관리 — 분류노드와 동일한 원리)
- 기관유형 ID
- 공식 홈페이지 URL
- 기관 식별자 (공공기관 코드, 사업자번호 등 외부 시스템과 매칭할 값)
- 데이터 수집 방식 (API / 웹크롤링 / 수동)
- 마지막 수집일
- 데이터 상태 (정상 / 오류 / 방치됨)

**RelationshipType (관계유형, 코드 관리)**
- 유형 ID, 유형명 (소속 / 감독 / 산하 / 주관 / 공동주관 / 운영·위탁 등)

요청하신 대로 최소 6종을 기본 제공하되, 데이터 추가만으로 새 유형(예:
"업무협약", "재위탁")을 늘릴 수 있게 코드 테이블로 관리한다.

**OrganizationRelationship (기관 관계)** — `상위기관_id` 하나만 쓰는
방식을 대체하는 핵심 엔티티
- 관계 ID
- 출발기관 ID
- 대상기관 ID
- 관계유형 ID
- **관계확인상태**: `확인됨` / `확인필요` / `추정` 중 하나
  (기본값은 절대 `확인됨`이 아니고, 공식자료로 검증된 것만 `확인됨`으로
  승격시킨다 — "AI가 임의로 추정해 연결하지 않는다"는 원칙을 이 필드로
  강제한다)
- 관계출처 (근거자료명 또는 URL — 예: "정부조직법", "기획재정부 공공기관
  지정 현황 2026", 기관 홈페이지 "산하기관" 페이지 등)
- 확인일
- 유효시작일 / 유효종료일 (기관 개편으로 소속이 바뀔 수 있으므로 관계에
  "기간"을 둔다 — 예: "A진흥원은 2024년까지 문체부 소속이었다가 2025년
  조직개편으로 새로 생긴 B청 소속으로 변경")
- 변경이력 (이 관계가 이전에 어떻게 기록돼 있었는지 로그 — 무엇이 언제
  바뀌었는지 추적 가능)

이렇게 관계를 독립 엔티티로 분리하면, 기관 하나가 **동시에 여러 관계**를
가질 수 있다. 예: 한국콘텐츠진흥원은 문화체육관광부에 "산하" 관계이면서,
특정 사업에서는 다른 협회와 "공동주관" 관계일 수 있다 — `상위기관_id`
필드 하나로는 이런 다양성과 시간 변화, 출처를 표현할 수 없다.

**ProgramOrganizationRole (지원사업 ↔ 기관, 역할 포함 다대다 연결)**
지원사업 하나에 여러 기관이 서로 다른 역할로 관여하는 경우를 위한 연결.
- 지원사업 ID
- 기관 ID
- 역할유형 ID (RelationshipType과 같은 코드 테이블을 공유 — 주관/공동주관/
  운영·위탁/예산지원 등)

예: "2026 AI 콘텐츠 제작지원"은 문화체육관광부가 `예산지원`, 한국콘텐츠
진흥원이 `주관`, 특정 협회가 `공동주관` 역할로 각각 연결된다.

### 화면 표시 규칙
- `확인됨` 관계만 기관구조 화면의 기본 트리에 실선으로 표시
- `확인필요` 관계는 "관계 확인 필요" 배지와 함께 별도 표시 (또는 아예
  숨기고 관리자 화면에서만 노출 — Phase 1 정책으로 결정 필요)
- `추정` 상태는 사용자 화면에 노출하지 않는다 (내부 검토용으로만 보관)

## 4. 출처 및 사실 단위 추적 구조

### 엔티티 정의

**SourceDocument (원문 문서)** — 공고와 관련된 원본 자료 하나
(웹페이지든 첨부 PDF/HWP든)
- 문서 ID
- 소속 지원사업 ID (또는 세부공모 ID)
- 문서유형 (웹페이지 / PDF / HWP / HWPX / 이미지 등)
- 원문 URL
- 첨부파일명 (해당 시)
- 수집일
- **원문 버전 / 파일 해시**: "파일 해시"란 그 문서 내용의 고유한 지문
  같은 것으로, 문서 내용이 한 글자라도 바뀌면 해시값도 달라진다. 이걸
  저장해두면 "공고문이 언제 수정됐는지"를 자동으로 감지할 수 있다.
- 수집방식 (API / 크롤링 / 수동 업로드)

**FactSource (사실 단위 출처)** — 핵심 신규 엔티티. 지원사업의 "항목"
하나하나에 붙는 근거.
- FactSource ID
- 지원사업 ID
- **필드명** (지원대상 / 신청자격 / 지원금액 / 신청기간 / 지원기간 /
  지원내용 / 사용가능비용 / 평가방법 / 제출서류 — Phase 1은 이 9개로
  시작하되, 필드명 자체도 목록에서 관리해 향후 새 항목(예: "ESG 관련
  조건")이 필요해지면 코드 수정 없이 추가할 수 있게 설계한다)
- 필드값 (실제 저장된 내용, 예: "인건비 사용 가능")
- 근거 문서 ID (SourceDocument 참조)
- 페이지번호 (PDF/HWP인 경우)
- 섹션/문단 (해당 위치 설명, 예: "3. 지원내용 > 가. 인건비")
- HTML 섹션/앵커 (웹페이지인 경우, 페이지번호 대신 사용)
- **확인상태**: `확인된 사실` / `AI 분석` / `추정` 중 하나
- 사람검수여부 (검수완료 / 미검수)
- 수집일

### 상세 화면에서의 표시 예시 (요청하신 형태 그대로)

```
인건비 사용 가능 — 확인된 사실
출처: 2026년 사업 공고문, p.12
[원문 열기]
```

페이지를 특정할 수 없는 웹페이지형 정보는:
```
지원 대상: 중소기업(업력 7년 이하) — 확인된 사실
출처: 한국콘텐츠진흥원 "2026 AI 콘텐츠 제작지원" 공고 페이지
      (수집일 2026.09.01)
[원문 열기]
```

AI가 요약하거나 판단을 제공한 경우:
```
"이 사업은 콘텐츠 제작 스타트업에 특히 유리할 수 있음" — AI 분석
근거: 위 지원대상·평가방법 항목 (원문 인용 보기)
```

이 구조 덕분에 상세 화면의 항목 하나하나가 "이 내용을 어디서 가져왔는지"를
클릭 한 번으로 확인할 수 있다 — 사업 전체에 링크 하나 걸어두는 것과는
신뢰도 차원이 다르다.

## 5. Program(지원사업) 엔티티 재정의

목록 화면은 여러 건을 빠르게 보여줘야 하므로 매번 FactSource를 조회해
조립하면 느리고 복잡하다. 반대로 상세 화면은 정확성이 생명이라 사실
단위 추적이 필요하다. 그래서 두 층으로 나눈다.

**Program (지원사업) — 목록에 필요한 "정리된 요약값"을 직접 보관**
- 지원사업 ID
- 사업명 (표시명 — 이것도 변경 이력 관리)
- 사업유형, 공고상태 (접수중/마감임박/마감/예정)
- 대표 신청기간 (요약값 — 목록 카드 표시용)
- 대표 지원금액 (요약값 — 목록 카드 표시용)
- 대표 대상기업 요약, 대표 지역 요약
- 등록일, 마지막 업데이트일

**FactSource(4번) — 상세 화면의 근거 있는 세부 항목**을 담당

**ProgramClassification(2번) / ProgramOrganizationRole(3번)**으로 산업·
기술·기관 연결을 담당

**SubProgram(세부공모), SelectedCompany(선정기업)**는 이전 설계문서의
구조를 그대로 유지하되, Phase 1에서는 필수 구현 대상이 아니다 — 다만
Program과 SourceDocument·FactSource 구조가 세부공모 단위로도 그대로
재사용되도록만 확인해두면 된다 (나중에 추가해도 구조를 안 바꿔도 됨).

이렇게 나누면, "목록 카드에 모든 정보를 넣지 않는다"는 지침과 "상세는
사실 단위로 출처를 추적한다"는 지침을 동시에 만족시키면서 화면 성능도
지킬 수 있다.

## 6. Phase 1 완료 기준 — 이 설계가 어떻게 충족하는지

| 질문 | 이 설계에서의 근거 |
|---|---|
| 새 기관의 공고를 추가할 수 있는가? | Organization·SourceDocument가 독립 엔티티라 신규 기관은 행 추가만으로 연결됨 |
| 새 산업 분야를 DB 구조 변경 없이 추가할 수 있는가? | ClassificationNode에 행 추가만으로 가능 (2번) |
| 하나의 공고를 여러 산업·기술에 연결할 수 있는가? | ProgramClassification이 다대다 구조 (2번) |
| 기관 간 여러 종류의 관계를 저장할 수 있는가? | OrganizationRelationship + RelationshipType 코드테이블 (3번) |
| 기관 관계의 출처와 확인일을 남길 수 있는가? | OrganizationRelationship의 관계출처·확인일 필드 (3번) |
| 상세 화면 핵심 사실마다 원문 위치를 확인할 수 있는가? | FactSource의 문서ID·페이지·섹션 필드 (4번) |
| 검색결과→상세로 자연스럽게 이동하는가? | 화면설계 문서(phase1-mvp-screens.md)의 이동 흐름 |
| 원문 공고·첨부파일을 직접 열 수 있는가? | SourceDocument의 원문URL·첨부파일명 (4번) |
| 수집일·마지막 업데이트일을 확인할 수 있는가? | SourceDocument.수집일, Program.마지막업데이트일 |
| AI 추정을 확인된 사실처럼 표시하지 않는가? | FactSource·OrganizationRelationship의 확인상태 필드가 `확인됨`이 아니면 별도 배지 강제 |

## 7. 개발 우선순위 (재확인)

1. **공고·기관·산업·출처 데이터 모델 확정** (이 문서)
2. 원문 수집 및 저장 (기업마당 API 1개 연동 + SourceDocument 저장)
3. 상세 화면 + 사실 단위 출처 표시 (FactSource를 실제로 화면에 그려서
   구조가 실전에서 맞는지 검증)
4. 목록 화면 (Program 요약필드 사용)
5. 키워드 검색 및 기본 필터 (산업/기술/지역/공고상태)
6. 최소한의 메인 화면 (검색 진입점만)
7. 기관별 화면 (최소 기능 — 데이터 검증 목적)
8. 기관구조 화면 (최소 기능 — 데이터 검증 목적, `확인됨` 관계만 표시)
9. 기업 프로필 · AI 매칭은 이후 단계 (Phase 2+)

화면을 먼저 여러 개 만들지 않고, **상세 화면 하나를 이 데이터 모델로
끝까지 구현해보는 것**을 최우선 검증 지점으로 삼는다. 상세 화면이 이
구조로 잘 작동하면 나머지 화면은 상대적으로 단순한 조합이다.
